# 멀티 EVTA 확장성 — 왜 4배가 아니라 2배인가 (2026-11-03)

ResNet-18, 4코어 비트스트림(`zcu102_4_1x16_i8w8a32_16_15_18_17.bit`),
`build_aarch64_multi`, cat_285, 스레드들이 공유 카운터로 100장을 나눈다.
도구: `scripts/board-scaling.sh`(측정), `ci/nt_instrument.py`(번들 복사본의
문장마다 시간을 재 연산 이름별로 평균). 계측 부담은 문장당 시계 두 번이라
무시할 만하다(계측 없는 4코어 CI 23.63 img/s 대 계측 23.79). oops 0, 오답 0.

## 1. 확장성

| 스레드(=VTA 코어) | 100장 | 처리량 | 1코어 대비 | 한 장 지연 |
|---|---|---|---|---|
| 1 | 8574ms | 11.66 img/s | 1.00 | 86.3ms |
| 2 | 5495ms | 18.20 img/s | 1.56 | 110.7ms |
| 3 | 4571ms | 21.88 img/s | 1.88 | 135ms |
| 4 | 4203ms | 23.79 img/s | 2.04 | 165ms |

같은 멀티 비트스트림 안에서 1→4 비교다. 이전에 적은 2.16배는 단일
비트스트림 1코어(91.6ms)를 분모로 쓴 값이다.
시작 비용(스레드 생성, 가중치 12MB 적재)은 약 50ms 로 전체의 1% — 원인이
아니다.

## 2. 한 장이 어디에 쓰이나 (ms, 스레드 평균)

| 연산 | 어디서 | 1스레드 | 4스레드 | 증가 |
|---|---|---|---|---|
| `convolution_wo_tr` (VTA 합성곱 19개) | **VTA** | 26.4 | 37–40 | +12 |
| `transpose_nhwc2vtaio` + `transpose_vtaio2nhwc` | CPU, 메모리 | 29.3 | 39–42 | +12 |
| `nonvtaconvolution` (첫 7x7 합성곱, 3채널) | CPU, OpenMP 4 | 14.5 | 44–60 | **+35** |
| `VTABufferAlloc` / `Free` (매 장 할당·해제) | 커널 드라이버 | 4.2 | 15–20 | +12 |
| `fullyconnected` | CPU | 3.7 | 5.2–7.3 | +2 |
| `elemadd` `maxpool` `elemsub/div` `quantize` 등 | CPU | 8.2 | 9–11 | +2 |
| **합** | | **86** | **160–172** | **+79** |

1스레드에서 **VTA 가 일하는 시간은 30%(26ms)뿐**이고 나머지 70%는 CPU
일이다. 레이아웃 변환(transpose)만으로 VTA 계산 시간보다 길다.

## 3. 간섭 실험 — 무엇이 무엇과 다투나

VTA 스레드 하나를 돌리면서 나머지 CPU 3개에 부하를 건다.

| 연산 | 부하 없음 | CPU 연산 부하 3 | 메모리 복사 부하 3 |
|---|---|---|---|
| VTA 합성곱 | 26.4 | 26.4 | 28.0 |
| transpose 둘 | 29.3 | 29.2 | **52.2** |
| CPU 합성곱 | 14.5 | **51.9** | **92.1** |
| VTABufferAlloc | 3.6 | 4.0 | **15.2** |
| fullyconnected | 3.7 | **8.1** | 11.0 |
| 한 장 | 86 | 128 | 212 |

- **CPU 합성곱은 CPU 4개를 다 쓴다.** `CPUBundle_aarch64.cpp` 에
  `#pragma omp parallel for num_threads(4)` 가 박혀 있어 `OMP_NUM_THREADS`
  로 바꿀 수 없다(1, 2 로 실험해도 변화 없음). 1스레드일 때는 놀던 CPU 를
  빌려 14.5ms 에 끝내지만 4스레드면 빌릴 CPU 가 없어 ~50ms — 순차 비용에
  가까워진다. **증가분의 절반(35ms)이 이것이다.**
- **transpose 와 버퍼 할당은 메모리 대역폭에 민감하다.** CPU 부하로는 그대로,
  메모리 부하로는 1.8배·4배.
- **VTA 합성곱은 CPU 메모리 부하에 거의 둔감**(26.4→28)하지만 4코어끼리는
  +45%. VTA 코어들이 같은 DDR 포트를 나눠 쓰는 몫으로 보인다(VTA 끼리
  간섭은 따로 분리하지 않았다).

## 4. 결론

4배가 안 되는 주원인은 **VTA 가 아니라 CPU 쪽**이다. 한 장의 70%가 ARM
A53 4개에서 도는 일이고, 그 CPU 4개는 4코어 모드에서도 4개 그대로다.
특히 첫 합성곱이 1코어 기준값에서 이미 CPU 4개를 다 빌려 쓰고 있었다.
그 다음이 메모리 대역폭(transpose, 버퍼 할당, VTA 끼리 DDR 공유)이다.
비트스트림이나 런타임 결함은 아니다.

## 5. 개선한다면 (하지 않았다 — 상류 컴파일러/런타임 변경)

효과 큰 순서 어림.

1. **연속된 VTA 층 사이의 transpose 를 없앤다.** 층마다 NHWC↔VTA 배치를
   왕복한다. VTA 배치를 유지하면 29ms(1코어)·40ms(4코어)가 대부분 사라진다.
   컴파일러(VTA 백엔드) 변경.
2. **VTA 버퍼를 매 장 할당·해제하지 않고 재사용한다.** 4코어에서 장당
   15–20ms. 번들 생성기 변경.
3. **첫 합성곱의 OpenMP 스레드 수를 멀티 모드에서 1로.** 순차 비용이
   그대로라 처리량 이득은 작을 것(스레드 과다·barrier 대기 정도). 재빌드
   필요, 실험 안 함.
4. 첫 합성곱(3채널 7x7)을 VTA 로 — 입력 채널 3이 VTA 블록(16)에 안 맞아
   CPU 로 빠진 것이라 패딩이 필요하다.
