# 14. 프로젝트 마무리 (2026-11-05)

ETRI NEST-C 컴파일러로 ZCU102 보드의 VTA/EVTA NPU 에서 CNN 추론을 돌리고,
컴파일 → 보드 실행 → 정답 대조까지 GitHub Actions 로 자동화했다.
숫자는 전부 보드 실측이며 근거는 `NEXT.md`, `results/`, 아래 CI 실행 번호에 있다.

## 1. 단일 코어 추론

| 모델 | 결과 | 장당 | 근거 |
|---|---|---|---|
| ResNet-18 | cat 281 / dog 207 / zebra 340 정답 | **91.6 ms** | model-test 41813475989 |
| ResNet-50 | cat 281 / dog 207 / zebra 340 정답 | **약 419 ms** | model-test 41813475989 |

- ResNet-18 확신도 0.478113 이 ETRI 배포본의 공개 기준값과 소수점까지 일치한다.
  ETRI 공개 수치(110 ms)보다 빠르다.
- ResNet-50
  - 상류 `CPUBundle_aarch64.cpp` 의 `transpose()` 가 미구현(`return -1`)이라
    입력과 무관한 고정 출력이 나왔다. 구현해서 정상 출력, 1,987 ms → 480 ms.
  - CI 에서 막힌 원인 셋은 전부 main 틀 쪽이었다.
    입력 이름이 `"data"` 로 고정, NCHW 입력을 NHWC 로 전치, Caffe2 모델에 BGR 대신 RGB 입력.
  - ETRI 사전 빌드 번들과 맞대어 번들 코드는 결백함을 확인했다.
- CPU 폴백: generic(순수 C) 1,475 ms 대 aarch64(NEON+ACL) 91.6 ms 로 16배.
  CI 기본은 aarch64 다.

## 2. 멀티코어 EVTA (4코어 비트스트림)

처리량(img/s), 괄호는 1코어 대비 배수.

| 모델 | 1코어 | 2코어 | 3코어 | 4코어 |
|---|---|---|---|---|
| ResNet-18 | 11.66 | 18.25 (1.67) | 21.88 | 24.21 (2.16) |
| ResNet-50 | 2.43 | 4.29 (1.77) | 5.60 (2.30) | 6.63 (2.66) |

전부 정답, 커널 oops 0건 (multievta 41815522975).

- **원인 ① 메모리.** VTA 컨텍스트마다 32 MB 명령 큐가 둘씩 잡혀 코어당 77 MB 였다(CMA 총 256 MB).
  `ci/patch_vta_max_xfer.py` 로 `VTA_MAX_XFER` 를 `1<<25` → `1<<24` 로 낮춰 코어당 45 MB,
  4코어 합계 179 MB. 보드 부팅 인자는 건드리지 않았다.
- **원인 ② 비트스트림.** 부팅 기본 비트스트림이 단일 VTA 였다.
  ETRI 4코어 비트스트림과 멀티 구성 런타임(버퍼 15/18/17)으로 바꾼다
  (`scripts/board-bitstream.sh multi`, 끝나면 `single` 로 되돌림).
- **예전 "4코어 통과" 는 착시였다.** 코어 1~3 스레드가 SError 로 죽고 코어 0 혼자
  100장을 처리했다. 지금은 실행 전후 `dmesg` oops 수를 비교해 판정한다.

## 3. 4배가 아닌 이유 (`results/scaling-20261103.md`)

- 1스레드 한 장 86 ms 중 **VTA 합성곱은 26 ms(30%)** 뿐이고 나머지는 CPU 일이다.
  - 레이아웃 transpose 29 ms
  - 첫 7×7 합성곱 14.5 ms (OpenMP `num_threads(4)` 고정)
  - 매 장 VTA 버퍼 할당 4 ms
- CPU 부하 / 메모리 부하 간섭 실험으로 CPU 경합과 메모리 대역폭으로 갈랐다.
  결함이 아니라 구조적 특성이다.
- ResNet-50 이 더 잘 늘어나는 것은 한 장에서 VTA 가 차지하는 몫이 더 커서다.

## 3-b. 벤치마크 — VTA 대 CPU 단독

같은 컴파일러의 CPU 백엔드(aarch64)로 VTA 없이 돌린 것과 비교했다(benchmark 41950655199).
VTA 가 CPU fp32 대비 ResNet-18 은 지연 **20.5배**·처리량 13.1배, ResNet-50 은
지연 **10.9배**·처리량 8.6배 빠르다. 표와 해석상 주의점은 `README.md` 의 벤치마크 절.

## 4. CI 자동화

- 러너: 연구실 서버 sota-AIP(192.168.1.150)의 systemd 서비스 `sota-aip`. 개인 PC 를 꺼도 돈다.
- 모델 하나 = `models/<이름>.conf` 파일 하나.
  푸시하면 보정 프로파일 → 번들 컴파일 → 보드 전송 → 추론 → 정답 대조,
  결과는 `results/latest.md` 로 자동 커밋된다.
- 보드가 한 대라 모든 워크플로를 `concurrency: zcu102-board` 로 묶어 순서대로 돈다.
- 상류 코드는 손으로 고치지 않고 `ci/patch_*.py` 로 매 실행 적용한다(멱등).
- CMA 관문: 실행 전 `코어 수 × (32 MB + 가중치) + 4 MB` 여유를 확인해, 누수가 있으면 시작하지 않는다.

| 워크플로 | 언제 | 하는 일 |
|---|---|---|
| `model-test` | `models/**`, `ci/**` 등 푸시 / 수동 | `models/*.conf` 전부 + ResNet-18 4코어 |
| `multievta` | `models-multi/**` 푸시 / 수동 | 멀티코어 처리량 |
| `debug-dump` | 수동 | 층별 중간 텐서 덤프 |
| `board-recover` | 수동 | check / kill / reboot |
| `board-health` | 2시간마다 | 보드 점검 |
| `build`, `board-test` | 매주 월요일 | 컴파일러·보드 런타임 재빌드 |

## 5. 보드 유지보수

- 전원 차단으로 깨진 SD 카드 ext4 비트맵을 그 카드에서 수리했다
  (`swapoff` → `sysrq u` → `e2fsck` → `sysrq b`). 지워진 데이터는 없다.
- 상류 결함 5건을 분석해 `patches/` 에 정리했다:
  transpose 미구현, concat, ReLU 포화, requant 반올림, 타일링 폴백.

## 6. 한계

- 4코어 효율은 2.2~2.7배에서 멈춘다. 층 사이 transpose 제거·버퍼 재사용이 필요하고
  둘 다 상류 컴파일러 변경이다.
- ResNet-50 4코어는 실행 중 CMA 여유가 2.8 MB 뿐이다. 3코어가 안정 구성이다.
- 비정상 종료하면 CMA 64 MB 가 반납되지 않는다. 회복은 보드 재부팅뿐이다.
- SqueezeNet 은 오답(905/904/533)으로 중단해 `models-off/` 로 뺐다.
  ResNet-50 에서 찾은 채널 순서·NHWC 전치가 유력한 원인 후보다.
- VGG-19 는 미해결이다.
- ResNet-50 확신도가 0.002 로 찍힌다. 모델 출력이 이미 softmax 인데 main 이 한 번 더
  거는 탓이며 순위에는 영향이 없다.
- 교내 방화벽 때문에 GitHub 클라우드 러너는 보드에 못 닿는다. self-hosted 러너가 필수다.

## 7. 사용법 — 모델 추가하고 돌리기

윈도우 PowerShell 기준. SOTA-PNU 조직 멤버는 모두 푸시 권한이 있다.

1. 클론
   ```sh
   git clone https://github.com/SOTA-PNU/nestc-zcu102.git
   ```
2. `models/resnet50.conf` 를 복사해 고친다.
   이름, ONNX 주소, 입력 이름·모양, 레이아웃(`NCHW`/`NHWC`), 채널 순서(`CHANNEL_ORDER`),
   기대 정답(`EXPECT`).
3. `git add` → `git commit` → `git push`. `main` 에 들어가면 model-test 가 자동으로 돈다.
4. 저장소 Actions 탭 → model-test 에서 진행을 본다.
   결과가 `results/latest.md` 로 자동 커밋되므로 다음 작업 전에 `git pull` 한다.
5. 멀티코어는 `models-multi/` 에 conf 를 넣고 푸시한다.
   수동 실행은 Actions → multievta → Run workflow.

고장났을 때

- Actions → board-recover → check / kill / reboot.
- 큐에만 쌓이면 Settings → Actions → Runners 에서 Offline 인지 먼저 본다.
- **VTA 추론 중에는 워크플로를 취소하지 않는다**(보드 재부팅이 필요해진다).
- 재부팅은 한 번만 보내고 90초 기다린다.
