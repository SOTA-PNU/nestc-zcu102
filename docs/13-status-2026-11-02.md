# 진행 현황 — 2026-11-02

`docs/12-status-2026-10-30.md` 의 뒤를 잇는다. 그 문서는 그날의 기록으로
남겨 두고, 그 뒤에 바뀐 것만 여기 적는다. 특히 **12번 문서의 성능 수치는
낡았다** — 1절을 먼저 읽어야 한다.

## 1. aarch64 가 상류의 기준 구성이었다 (가장 큰 수정)

지금까지 보드 빌드를 `build_board`(generic) 으로 재 왔는데, 그것이
곁길이었다. CPU 폴백에는 두 구현이 따로 있다.
`NESTC_EVTA_RUN_WITH_GENERIC_BUNDLE` 로 갈리며, generic 은 순수 C 이고
aarch64 는 NEON 과 ARM Compute Library 를 쓴다. **서로 독립된 구현이다.**

ResNet-18 한 장 기준으로 generic 1475ms, aarch64 **91.6ms** — 16배다.
게다가 aarch64 쪽 확신도 **0.478113** 이 ETRI 배포본의 공개 기준값과
소수점까지 일치한다. generic 은 0.533373 으로 다르다. 즉 상류가 재고
배포한 것은 aarch64 구성이고, 우리가 "느리다" 고 적어 온 수치는 쓰지 않는
경로를 잰 것이었다. ETRI 가 공개한 110ms 보다도 우리 쪽이 빠르다.

CI 의 기본 보드 빌드를 `build_aarch64` 로 바꿨다. 12번 문서의 1478ms 는
generic 수치이므로 인용하지 않는다.

이것이 SqueezeNet 수사에도 큰 뜻이 있다. 두 CPU 폴백은 서로 독립된
구현인데 **둘 다 똑같이 틀린 답(905/904/533)을 낸다.** 독립된 두 구현이
같은 오답에 수렴할 확률은 낮으므로, CPU 폴백 전체가 용의선상에서
빠진다.

## 2. 멀티 EVTA — 코어를 늘려도 빨라지지 않는다

2코어 번들은 빌드·링크·실행까지 전부 성공했다. 그런데 처리량이 늘지
않았다. 한 장당 90.7ms, 초당 11.02장 — 단일 코어(91.6ms, 초당 10.9장)와
사실상 같다. 1.01배다.

4코어는 아예 못 돌린다. `board-multi-run.sh` 가 실행 중 `CmaFree` 를
3초마다 재서 코어당 사용량을 실측했는데 **약 76MB** 였다. 네 코어면
310MB 가 필요한데 보드의 CMA 총량은 256MB(`CmaTotal: 262144 kB`)다.
물리적으로 불가능하다. CMA 부팅 인자를 늘리는 방법이 있으나, 잘못 넣으면
누가 가서 SD 카드를 뽑아야 하므로 원격으로는 건드리지 않는다.

2코어가 안 빨라지는 이유로 지금 가장 유력한 것은 **VTA 런타임이 명령
제출을 전역으로 직렬화한다**는 것이다. 그러면 코어가 넷이어도 한 번에
하나만 일한다. 확인하려면 런타임(`vta/vtalib`)의 명령 큐가 코어별인지
전역 잠금인지 소스에서 봐야 하는데, 그 파일이 아직 손에 없다. 받으면
바로 볼 것이다.

## 3. CMA 가 샌다 — 상류 결함으로 보고할 것

정상 종료해도 조금씩 반납되지 않는다. 재부팅 직후 250MB 였던 것이 몇 번
돌리면 175MB 가 되고, 어젯밤 네 모델을 연달아 돌린 뒤에는 **11MB** 까지
떨어져 있었다. 비정상 종료하면 그 프로세스 몫이 재부팅 전까지 통째로
돌아오지 않는다.

증상이 고약한 것은, 메모리가 모자란 상태로 실행하면 원인이 안 보이는
형태로 죽기 때문이다. `dat_queue.h:39: Check failed: fpga_buff_ != nullptr`
와 스택 트레이스만 남는다. 어젯밤 SqueezeNet 실패가 바로 이것이었는데,
하마터면 905 오답 문제가 다시 나빠진 것으로 오해할 뻔했다.

`board-build-run.sh` 가 실행 전에 `CmaFree` 를 재서 모자라면 분명한
메시지로 멈춘다. 관문은 처음 40000 kB 였는데 실측 76MB 보다 낮아서
어젯밤 그대로 통과해 버렸다. **80000 kB 로 올렸고**, 실행이 끝난 뒤에도
한 번 더 찍어 모델마다 얼마씩 새는지 보이게 했다.

## 4. SqueezeNet — 범위가 많이 좁았다

지금까지 배제한 것: Concat 알고리즘과 번들이 내보내는 인자, 2의 거듭제곱
양자화, 낡은 번들, 입력 레이아웃과 전치, VTA 연산 의미(인터프리터는
281/207/340 으로 정답), 합성곱 타일링, ReLU 포화, 맥스풀, 평균풀,
분류기 합성곱, **CPU 폴백 전체**(1절), 그리고 재양자화의 버림.

마지막 것은 가설을 세웠다가 스스로 기각한 경우다. 보드가 `sum >> shift`
로 버리는 것이 오차의 원인이라고 보았는데, `VTAInterpreterNodes.cpp`
924행과 1084행을 보니 **인터프리터도 똑같이 버린다.** 인터프리터는
정답을 내므로 버림은 원인이 아니다. 반올림 패치는 그 자체로는 정확도에
이로우므로 남겨 두되 환경 변수로 꺼 둔 상태이고, `patches/` 의 문서에
기각이라고 적었다.

남은 범위는 **인터프리터가 지나가지 않는 길**뿐이다. 인터프리터는
`VTASave` 를 거치지 않으므로, "인터프리터가 맞다" 는 그래프 의미가
맞다는 뜻이지 **생성된 번들 코드가 맞다는 뜻이 아니다.** 즉 `VTASave`
가 찍어 내는 코드와 `VTABundle.cpp` 의 타일링·패킹·명령 생성이 남았다.

가장 유력한 가설은 SqueezeNet 의 squeeze 층이 **16채널**이라는 점이다.
VTA 출력 블록 하나와 정확히 같아서 가상 스레드가 1로 고정된다. 반면
튜닝 표(`VTASchedules.h`)의 11개 항목은 전부 ResNet 모양이고 가상 스레드
2에 출력 채널 64 이상이다. 상류가 한 번도 돌려 본 적 없는 조합이다.

## 5. 이분 탐색은 접고 기대값 대조로 바꿨다

ONNX 를 중간에서 잘라 인터프리터와 보드를 비교하려던 방식은 **비교
지표가 성립하지 않아** 접었다. 잘린 모델의 출력은 4차원 특징맵이라
argmax 가 뜻이 없다. 인터프리터는 `Label-K1: 0 (probability: 0.0000)` 을
내고 보드는 `Result:` 줄 자체를 안 찍는다. 자르고 컴파일하는 것까지는
다 됐으므로 도구(`ci/cut_onnx.py`)는 남겨 둔다.

대신 층별 덤프를 쓴다. 기준값은 **번들 소스에서 읽는다.** 생성된 .cpp
에 양자화 스케일이 상수로 박혀 있다(`nonvtaconvolution(..., 1.0/32.0, ...)`).
거기에 보정 프로파일의 실수 범위를 곱하면 그 층이 내야 할 int8 최대값이
나온다. 실제 덤프와 크게 다르면 그 층에서 틀어진 것이다.

스케일 규칙도 확인했다. ResNet-18 의 스케일 18개를 보정 범위와 맞춰
보니 예외 없이 **스케일의 역수 = 2^floor(log2(127/최대절대값))** 이었다.

처음 판에서 한 번 속았다. 덤프 이름을 접두사로 느슨하게 맞췄더니 멀쩡한
층이 어긋난 것처럼 보였다 — Glow 이름 끝의 `__1` `__2` `__7` 이 서로
다른 텐서(같은 층의 양자화 전/후)이기 때문이다. **맞는 모델에 먼저
돌렸기 때문에** 잡았다. 도구를 새로 만들 때는 정답을 아는 입력으로
먼저 검증한다.

## 6. 연구실 서버 — vcu118-dev

교내망 안에 있는 것을 확인했다. 서버에서 `sota.pusan.ac.kr:25022` 가
열리고 키 등록 뒤 비밀번호 없이 보드에 들어간다. GitHub 클라우드 러너는
같은 주소에 종료 코드 255 로 실패하므로, 이것이 이 기계를 고른 이유다.

걸리는 것이 둘 있다. 하나는 **메모리**다. 총 15GB 중 Vivado 가 13.7GB 를
쓰고 있어 쓸 수 있는 것이 1.9GB 뿐이다. 계정이 `sota` 공용이라 누구
작업인지는 물어봐야 안다. 그래서 받기(도커 이미지, 상류 클론)만 먼저
하고 컴파일러 빌드는 그 작업이 끝난 뒤로 미뤘다.

다른 하나는 **VirtualBox NAT** 다. 이 기계는 가상머신이고 나가는 통신만
된다. CI 에는 영향이 없지만 — 러너도 보드 SSH 도 전부 나가는 방향이다 —
개인 PC 에서 1.4GB 트리를 밀어 넣을 수 없다. 서버가 직접 클론하는 것으로
풀었다. 개인 PC 의 트리는 상류 HEAD 보다 커밋 하나만 앞서 있고 그 커밋은
GitHub 미러에 있다. 작업 디렉터리의 수정 세 개는 `ci/` 의 패치
스크립트가 매번 다시 만들므로 옮길 필요가 없다. **상류를 손으로 고치지
않고 스크립트로 유지해 온 선택이 여기서 값을 했다.**

## 7. 다음

런타임이 명령 제출을 직렬화하는지 소스에서 확인한다. 이것이 멀티 EVTA
를 더 파도 되는지를 가른다.

기대값 대조를 **ResNet-18 로 먼저 검증**하고, 통과하면 SqueezeNet 에
돌려 처음 어긋나는 층을 찾는다.

연구실 서버는 Vivado 가 끝난 뒤 컴파일러를 빌드하고 러너를 등록한다.

상류에 보고할 것이 다섯 건이 되었다. Concat 번들 경로 부재와
`llvm_unreachable`, 타일링 기본값, ReLU 재양자화 포화, 재양자화 반올림,
CMA 누수.
