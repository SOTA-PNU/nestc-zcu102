# 진행 현황 — 2026-10-30

## 요약

ResNet 계열은 보드에서 안정적으로 돌고, 모델을 올리고 결과를 받는 과정이
자동화되었다. 오늘의 성과는 **ResNet 이 아닌 모델을 VTA 에 올릴 때 걸리는
상류의 구조적 한계 세 가지를 찾아낸 것**이다. 두 가지는 고쳤고, SqueezeNet 의
오답은 원인 범위를 FPGA 실행 경로의 CPU 폴백 구간으로 좁혔다.

## 되는 것

보드와 비트스트림, 런타임은 정상이다. 상류 ZCU102 테스트 51 개가 모두 통과하고,
ResNet-18 은 `cat 281 / dog 207 / zebra 340` 을 장당 1478ms 에 낸다.
ResNet-50 도 돈다(상류가 aarch64 경로에서 빼 두었던 것을 되살렸다).

모델 하나는 설정 파일 하나로 기술한다. `models/` 에 올려 푸시하면 보정 프로파일
생성, 번들 컴파일, 보드 전송, 추론, 정답 대조까지 사람 손 없이 돌고 결과가
저장소에 다시 커밋된다. 보드 상태는 2시간마다 자동으로 점검되고, 이상이 있으면
메일이 온다. 이 점검은 GitHub 클라우드에서 돌기 때문에 연구실 PC 가 꺼져 있어도
동작한다.

## 오늘 찾은 상류의 한계

**Concat 이 번들 경로에 없었다.** Glow 는 Concat 을 `TouchInst` 와
`InsertTensorInst` 로 내리는데, VTA 백엔드는 인터프리터 쪽에만 구현이 있고
AOT 번들 쪽에는 없었다. 게다가 미지원 명령을 만나면 `llvm_unreachable` 로
빠지는데 Release 빌드에서는 그것이 정의되지 않은 동작이라, 증상이 엉뚱한
모습으로 나타나 원인이 가려졌다. 구현을 넣고 미지원 명령은 이름을 찍고 멈추도록
바꿨다. SqueezeNet 번들 생성이 처음으로 성공했다.

**컨볼루션 타일링이 ResNet 전용 표였다.** 타일 크기는 알고리즘이 아니라 레이어
모양 열 개를 통째로 외운 손튜닝 표에서 가져온다. 표에 든 열한 항목은 전부 ResNet
모양이고, 하나도 맞지 않으면 `1, 14, 14` 라는 고정값으로 떨어진다. 표의 항목을
전부 계산해 보면 **폭 방향 타일링은 한 번도 쓰인 적이 없다.** 즉 출력 폭이 14 의
배수가 아닌 모델은 상류가 검증한 적 없는 경로로 들어간다. 기본값을 "폭은 나누지
않고 높이만 타일" 로 바꿨다. 모델에 무관한 규칙이다.

**독립 ReLU 에 int8 포화가 없었다.** 컨볼루션에 합쳐지지 않은 ReLU 는 재양자화
배율을 `int` 로 자른 뒤 `int8_t` 에 그대로 곱한다. 배율이 2 면 값 100 이 -56 으로
뒤집히고, 배율이 1 미만이면 전부 0 이 된다. 인터프리터는 int32 로 계산한 뒤
포화시킨다. 번들도 같게 고쳤다.

세 가지 모두 SqueezeNet 전용 수정이 아니라 일반적인 것이며, 그대로 ETRI 에
보고할 수 있다. VTAInterpreter 의 명령 디스패치에 `TouchInst` 분기가 없어
Concat 이 있는 모델은 인터프리터에서도 시작하자마자 죽는 문제도 함께 찾았다.

## SqueezeNet — 남은 문제

보드에서 `905 / 904 / 533` 으로 틀린다. 오늘 범위를 크게 좁혔다.

같은 모델을 같은 보정 프로파일로 **VTAInterpreter 에서 돌리면
`281 / 207 / 340` 으로 전부 맞는다.** VTAInterpreter 는 VTA 의 연산 정의와 int8
양자화를 그대로 쓰되 FPGA 대신 소프트웨어로 계산한다. 그것이 맞는다는 것은
Concat 구현, 양자화 스케일, 연산의 정의가 모두 옳다는 뜻이다. 남은 차이는 번들
실행 경로에만 있다.

배제한 것을 적어 둔다. Concat 알고리즘과 인자(numpy 대조), 2의 거듭제곱 int8
양자화, 보드 번들의 최신 여부, 입력 레이아웃과 전치, 컨볼루션 타일링(기본값을
바꿔도 결과가 비트 단위로 동일했다), ReLU 포화(같은 이유), maxpool, avgpool,
분류 컨볼루션의 스케일 처리.

다음 수는 추측을 그만두고 층별로 가리는 것이다. 번들을 계측 모드로 만들어 층마다
중간 텐서를 떨구고, 실행 순서대로 분포를 훑어 처음 망가지는 지점을 찾는다.
도구는 만들어 두었고 수동 실행만 하면 된다.

## 멀티 EVTA — 착수

비트스트림은 EVTA 코어 네 개를 담고 있는데(`VTA_DEVICE_NUM=4`, 코어별 레지스터
주소 0xA0000000~0xA0030000) **지금까지 모든 번들이 코어 0 하나만 썼다.** 즉
하드웨어의 1/4 만 쓰고 있었다.

상류 방식은 모델을 쪼개는 것이 아니라, 같은 모델을 코어 수만큼 컴파일해 각각
다른 코어에 묶고 여러 스레드가 동시에 돌리는 것이다. 한 장의 지연시간은 줄지
않고 **처리량**이 늘어난다. 지연시간까지 줄이려면 모델 분할이 필요하고, 상류
트리의 `onnx_yaml-parser` 에 그 흔적(파티션 기술서)이 있다.

4코어 번들은 빌드와 링크까지 성공했으나 실행 중 FPGA 연속 메모리(CMA) 할당에
실패했다. 코어마다 가중치와 활성 버퍼를 따로 잡기 때문이다. 코어 수를 조절할 수
있게 만들어 2코어와 4코어를 모두 돌려 보려 한다. 2코어가 되면 CMA 가 모자란
것이고, 2코어도 안 되면 멀티코어 자체를 더 봐야 한다.

## 교수님께 여쭐 것

**비트스트림.** SD 카드 기본 부팅 상태의 비트스트림이 multi-EVTA 4코어라고
판단했습니다. 근거는 빌드가 조건 없이 `VTA_DEVICE_NUM=4` 와 네 벌의 코어별
레지스터 주소를 박는다는 점, 그리고 2021년 트리에 살아 있는
`VTA_DEVICE_NUM > 2` 검사가 실제로 걸렸다는 점입니다. 비트스트림이 BOOT.BIN
안에 헤더 없이 들어 있어 파일에서 직접 확인할 방법은 찾지 못했습니다. 맞는지
확인해 주시면 멀티코어 작업을 확신을 갖고 진행하겠습니다.

**연구실 서버.** 지금은 빌드와 CI 가 개인 PC 에서 돕니다. PC 가 꺼져 있으면
아무것도 돌지 않고, 오래 꺼져 있으면 GitHub 가 러너 등록을 지웁니다(실제로
한 번 겪었습니다). 항상 켜진 기계로 옮기면 "푸시하면 알아서 돈다" 가 성립합니다.
필요 사양과 순서는 `docs/10-lab-server-setup.md` 에 정리해 두었습니다.

**상류 보고.** 위의 결함들을 ETRI(yongin.kwon@etri.re.kr)에 전달할지,
전달한다면 어느 범위까지 할지 정해 주시면 정리해 보내겠습니다.
